=================================================
4. ARCHIVOS PRINCIPALES
=================================================

src/ingest.py
-------------

Responsabilidad:

- Leer los documentos PDF.
- Extraer el contenido.
- Dividir el contenido en fragmentos.
- Generar embeddings.
- Construir y guardar el índice FAISS.
- Guardar la metadata necesaria para identificar:
  - Documento fuente.
  - Página.
  - Fragmento.

Es el proceso de preparación del conocimiento.

Normalmente se ejecuta cuando:
- Se agregan nuevos manuales.
- Se modifican documentos.
- Se desea reconstruir el índice.

No es necesario ejecutarlo para cada pregunta.


src/retrieval.py
----------------

Responsabilidad:

- Cargar el modelo de embeddings.
- Cargar el índice FAISS.
- Recibir una pregunta.
- Convertir la pregunta en embedding.
- Buscar los fragmentos semánticamente más cercanos.
- Retornar los resultados con:
  - source
  - page
  - text
  - score

La interfaz utilizada por rag.py quedó conceptualmente así:

    search(question, top_k=3)


src/rag.py
----------

Responsabilidad:

- Cargar las variables del archivo .env.
- Consultar retrieval.py.
- Recuperar los 3 fragmentos más relevantes desde FAISS.
- Construir el contexto.
- Enviar contexto + pregunta a Azure OpenAI.
- Obtener la respuesta del modelo.
- Mostrar:
  - Respuesta.
  - Fuentes recuperadas.
  - Páginas.
  - Scores/distancias.

El modelo configurado fue:

    gpt-5.4-mini


.env
----

Contiene las credenciales y configuración de Azure OpenAI.

La estructura utilizada es:

AZURE_OPENAI_ENDPOINT=https://rag-transformadores-2-resource.openai.azure.com
AZURE_OPENAI_API_KEY=TU_CLAVE_REAL
AZURE_OPENAI_DEPLOYMENT=gpt-5.4-mini

La clave real NO debe compartirse ni subirse a GitHub.

H. PRIMER ERROR DE RETRIEVAL
----------------------------

Al realizar una pregunta apareció:

    TypeError: search() got an unexpected keyword argument 'k'

La causa fue una diferencia entre rag.py y retrieval.py.

Se tenía:

    search(question, k=k)

y se corrigió por:

    search(question, top_k=k)

porque retrieval.py esperaba el parámetro:

    top_k


I. SEGUNDO ERROR: AZURE OPENAI 404
----------------------------------

Después de corregir FAISS, el flujo llegó hasta:

    Consultando Azure OpenAI...

pero apareció:

    NotFoundError: Error code: 404
    Resource not found

Se corrigió la configuración del cliente para utilizar la ruta
compatible con la API Responses actual:

    from openai import OpenAI

y:

    client = OpenAI(
        api_key=AZURE_OPENAI_API_KEY,
        base_url=f"{AZURE_OPENAI_ENDPOINT.rstrip('/')}/openai/v1/"
    )

La llamada quedó conceptualmente así:

    response = client.responses.create(
        model=AZURE_OPENAI_DEPLOYMENT,
        ...
    )

Después de este cambio, la llamada a Azure OpenAI funcionó.

-------------------

    Fragmento de texto
            |
            v

PASO 4 — FAISS
--------------

Los vectores se almacenan en un índice FAISS local.

Esto permite realizar búsqueda semántica eficiente:

    Pregunta:
    "¿Cómo inspeccionar el transformador?"

No es necesario que la pregunta use exactamente las mismas palabras
que el documento.

                 |
                 v


PASO 5 — RETRIEVAL
------------------

retrieval.py:

1. Convierte la pregunta en embedding.
2. Busca los vectores más cercanos.
3. Recupera top_k = 3 fragmentos.
4. Retorna documento, página, texto y score.

                 |
                 v

----------------------------------

                 v

El prompt de instrucciones restringe el comportamiento del modelo:

- Responder usando únicamente el contexto recuperado.

- Generar una respuesta técnica y concisa.

8. QUÉ DEMOSTRAMOS CON EL EXPERIMENTO
=================================================

El proyecto demuestra una arquitectura RAG híbrida:

    LOCAL
    -----
    - Documentos.
    - Embeddings.
    - FAISS.
    - Retrieval.

    CLOUD / AZURE
    ------------
    - Microsoft Foundry.
    - Azure OpenAI.
    - Modelo gpt-5.4-mini.

Por tanto, no se envía el manual completo al LLM en cada pregunta.

El proceso es:

    Recuperar solo los fragmentos relevantes
                    +
    Enviar esos fragmentos al modelo
                    =
    Generar una respuesta contextualizada


Esto aporta:

- Menor volumen de contexto.
- Mayor trazabilidad.
- Posibilidad de actualizar el conocimiento sin reentrenar el LLM.
- Separación entre conocimiento y generación.
- Control sobre las fuentes utilizadas.
- Uso de un modelo administrado en Azure.
